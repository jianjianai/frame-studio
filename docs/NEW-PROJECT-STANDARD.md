# 新增工程与文件修改规范

生效：2026-09-28。适用于 FRAME 仓库中的代码、目录、依赖、工具与协作操作。**本规范不规定动画制作方式、创作流程、交付标准或音乐水准。** 具体任务的内容要求不自动成为仓库规则。

## 1. 修改前确认范围

先读 `AGENTS.md`、本文件和目标模块的工程说明，再执行 `git status --short --branch`、查看最新提交及相关 diff。先确认哪些文件属于当前任务，哪些是其他任务的未提交改动。

只改解决当前工程问题需要的文件。修改前重新读取目标文件；文件或 HEAD 在期间发生变化，先合并再继续。不要用旧版本整文件覆盖新内容。小改动使用小补丁，避免顺手格式化整个仓库或重排无关代码。

存在其他任务改动时，不使用 `git add .` / `git add -A`，不擅自 stash、reset、clean、删除目录或结束所有 Node/浏览器进程。共享文件改动必须保留其他任务内容，提交前逐文件检查暂存区。

## 2. 文件存放位置

| 位置                                       | 存放内容                                           | 修改边界                                           |
| ------------------------------------------ | -------------------------------------------------- | -------------------------------------------------- |
| `src/projects/<id>/`                       | 单个工程源码、`project.ts`、`scene.ts` 及私有模块  | 工程内部可以按需要拆分；不引用其他工程的私有源码   |
| `src/engine/`                              | 公共运行协议、加载器、时间控制和可复用模块         | 仅在确有公共需求时修改，并验证现有调用者           |
| `src/ui/`、`src/App.tsx`、`src/styles.css` | 工作台与公共播放器                                 | 新增工程通常不需要修改；公共功能变更单独说明       |
| `public/films/<id>/`                       | 新工程的浏览器运行资源                             | 资源按工程隔离，使用相对路径，不写入其他工程目录   |
| `production/<id>/README.md`                | 工程说明入口：目录、依赖、脚本、输入输出和测试命令 | 只记录工程信息，不要求分镜、创作审核或音乐指标     |
| `production/<id>/` 其他文件                | 非运行时源文件、参数、资源来源与许可证记录         | 不放入 public；是否进 Git 按大小和可再分发条件决定 |
| `scripts/projects/<id>/`                   | 工程专用处理脚本                                   | 需要时创建；只修改本工程的明确输出                 |
| `scripts/`                                 | 公共脚手架、校验、构建和资源工具                   | 不把每个新工程的临时脚本不断堆在根部               |
| `tests/unit/`、`tests/e2e/`                | 单元测试与浏览器回归                               | 以模块或工程命名；共用测试不得写死工程数量         |
| `docs/`                                    | 公共工程说明、变更与审查记录                       | 文档链接和命令必须有效                             |
| `exports/<id>/`、`.cache/`、`.logs/`       | 生成结果、下载缓存、临时文件与日志                 | 不提交 Git；不要把工具输出写到仓库根目录           |

已有 `public/audio/<id>.*`、`public/posters/<id>.*`、`public/research/<id>.html` 以及三个 Demo 的 `production/music/` 可以保留。旧工程缺少独立 README 时补一个工程索引即可，不强制搬迁大文件、不制造两份真源。

`id` 使用小写英文开头的字母、数字和单连字符，最长 64 字符，不使用 Windows 保留名称。目录名、元数据 id 与路由 id 一致。文件命名优先小写连字符；操作系统启动脚本等已有中文文件不因此改名。

## 3. 新建与自动注册

```powershell
pnpm animation:new example-project "示例工程" --renderer pixi
pnpm project:check example-project
```

脚手架创建 `scene.ts`、`project.ts`、独立占位资源、工程 README 与浏览器测试文件。先在忽略目录内准备文件，依赖文件就位后再发布完整工程目录，不能先暴露指向缺失 `scene.ts` 的注册入口。脚手架遇到已存在的源码、资源、README 或测试文件时拒绝覆盖。

工程通过 `src/projects/*/project.ts` 自动发现。新增工程不应手工改公共列表、总数或路由分支。`project.ts` 使用静态字面值或本文件常量，`load` 保持 `() => import('./scene')`；元数据导入不启动渲染、不请求网络、不产生文件写入。`status` 只按接口枚举验证，检查器不根据标题、时长、内容或声音判断它该取哪个值。

## 4. 代码接口与资源生命周期

场景维持 `createScene({width,height,quality}) -> {canvas, render(time), dispose()}`。公共播放器负责调度，`render(time)` 接受绝对时间，可直接调用、倒退和重复调用；不依赖上一帧的执行历史。

场景不启动独立 `requestAnimationFrame`、`setInterval`、库内自运行 ticker 或单独音频时钟。使用 GSAP、骨骼、粒子或其他库时，适配公共时间接口即可；不限定实现技术。随机状态采用固定种子，不能让墙上时钟或每帧随机数决定回放结果。新的调度能力需通过公共接口扩展并补测试，不私下绕过播放器。

`project.audio` 是当前接口的可选本地资源路径；没有该字段不是工程违规。需要扩展资源/音频接口时说明兼容性并验证调用者，不把接口能力写成创作流程要求。

`dispose()` 释放本实例创建的 timeline、事件、几何、材质、纹理、GPU 和画布资源；异步初始化失败同样回收已创建对象。共享缓存不能被单个实例误删。浏览器场景不 import Node、文件系统或处理脚本。

资源通过 `assetUrl()` 或元数据相对路径加载。运行资源在本地 public 下，路径不含盘符、协议、查询参数、目录穿越或跳出 public 的符号链接。第三方依赖与资产随附来源和许可证文件，不提交密钥、环境私有配置或无再分发权限的原文件。

## 5. 处理脚本与文件写入

脚本在工程 README 写明输入、输出、依赖、执行命令以及是否覆盖现有输出。检查命令默认只读；生成/更新命令的名称和参数明确表示写入行为。不要在检查结束时顺便覆盖海报、音轨或索引。

写入只限目标工程。默认拒绝意外覆盖；明确的重建命令可以替换其声明的同名生成文件，但不能覆盖原始源文件或其他工程结果。共享 `assets.json` / `waveforms.json` 更新前重新读取，只修改目标条目，保留未知条目；并行写入通过独立工作区或串行协调，不依赖最后写入覆盖前者。

封面更新使用 `pnpm posters --project <id>`；全量操作必须显式 `pnpm posters --all`。缺输入、解析/解码失败、外部命令非零时清楚返回失败，不能保留旧缓存后仍声称本次生成成功。避免部分失败留下已被宣称完成的输出。

Node 脚本使用文件 API 和参数数组调用子进程，正确处理空格、中文路径和退出码；支持已有 `FFMPEG_PATH`、`FFPROBE_PATH`、`FRAME_BROWSER` 等环境配置，不写死个人电脑上的可执行文件路径。

## 6. 依赖和配置

统一使用 pnpm；依赖通过 pnpm 命令修改，同时提交 `package.json` 与 `pnpm-lock.yaml`，验证 `pnpm install --frozen-lockfile`。不手工编造 lockfile，不混入 package-lock/yarn.lock，不修改 node_modules 后当成源码修复。

按运行时/开发工具实际用途选择 dependencies/devDependencies，增加依赖需有当前用途；不得为可能的将来堆叠重复框架。维护命令名称与文档一致，避免与 pnpm 内置命令重名。

## 7. 测试与并行协作

```powershell
pnpm project:check                     # 结构、引用与明显接口错误；显示工程归档警告
pnpm project:check example-project --strict  # 将目标工程的警告也视为失败
pnpm verify                            # 工程检查、类型、单元、构建、浏览器回归
```

`project:check` 只检查代码与工程结构，不进行动画内容、音乐、审核或交付判断。它也不替代运行测试、资源泄漏检查和许可证权利核实。不要为了过测试改掉有意义的断言或隐瞒失败。

共用列表/筛选测试从源码元数据计算预期，不从页面结果反推预期，也不写死总工程数、某渲染类型数量。工程专属测试不混进无关项目。改变公共接口、加载/释放、路径或写入行为时补相应回归测试。

并行任务优先独立分支及 git worktree。各工作区有独立构建目录、测试报告与端口。浏览器测试使用 `FRAME_TEST_PORT`，默认不复用未知服务，避免测到他人的旧构建。端口被占用时选择自己的空闲端口，不关闭他人的服务器。只在实际需要时启用局域网访问，不将开发服务器默认暴露公网。

## 8. Git 与文档维护

提交前检查文件清单、diff、暂存区、敏感内容和相关测试；共享文件按补丁拆分，不附带别人的工程。保留现有历史，不强推。测试的是哪份源码，就记录对应提交或源文件范围；提交内容与测试对象不同时重新验证必要范围。

工程文档中的本地路径、文件名、命令和入口保持有效。移动/删除文件时同步更新 import、脚本、配置、测试和文档引用；不得留下假入口。已存在的业务或制作文档不自动成为全仓库规范。

存量问题见 `PROJECT-AUDIT-2026-09-28.md`。新目录规则采取渐进整理：发现时记录影响范围，优先修复会破坏整个工作台的引用、并行写入与测试问题，不批量重写他人的工程。
