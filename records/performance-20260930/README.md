# Frame Studio 性能审查 · 2026-09-30

目前的小规模基础操作性能正常，但大素材编辑、并发锁、构建素材处理和反复审片有明确瓶颈。最优先修复的是批量编辑中的同步全量哈希：只改少量文本也会三次读取所有素材，并阻塞整个 API 进程。没有证据支持当前需要更换 Web 框架、数据库或整体推倒引擎。

## 基线与结论边界

- 审查分支：`audit/performance-20260930`。
- 工作树：`/home/agentdock/AgentDock/frame-studio-performance`。
- 源码基线：`5a9d970`，package 7.5.1。生产采样 revision 为 `fc1bf50`；两者之间的提交只调整执行器浏览器进程权限。
- 本次为源码审查和性能测量，交付物位于本目录，业务代码未改动。
- 覆盖平台 HTTP MCP、本地持久 MCP、源码/合成/音频编辑公共链路、文件检索、检查点、SQL 与项目锁、素材索引、Git、任务与实时通知、预览/导出准备、Canvas/Remotion 单帧、前端构建与公开静态资源缓存。
- 生产只进行 SELECT-only 数据采样、文件元信息/只读读取和公开页面 HEAD/GET。数据库探针通过连接参数强制 `default_transaction_read_only=on`，另外拒绝非 SELECT/EXPLAIN SQL。没有在生产提交编辑、合成素材、启动任务或做并发压力测试。
- 放大问题的基准使用独立临时 PostgreSQL、合成作品和专用测试容器。Node 24.21.0、2 CPU 配额；主要基准/渲染容器内存上限 3 GiB。素材为真实写入的文件，结果反映热文件系统场景，不代表冷磁盘或公网延迟。
- 多数项目重复 3/5/10 次，保留全部样本；2 次审片/冷扫描只说明该次范围，不报告 P95 或容量上限。HTTP MCP 时间来自真实 Fastify 路由的 app.inject，包含认证、SDK 和业务处理，不含公网 RTT。
- 未进行整片编码、真实 3D/GPU 帧率、长对话滚动、整小时音频和多用户生产负载压测。这些不能由空白单帧或基础读取结果替代。

## 优先修复：5 项 P1

### P1-1 · 源码和文档批量编辑同步三遍哈希，阻塞整个 API

位置：`scripts/project-service.mjs` 的 edit/checkpoint/fingerprint，`scripts/production-input.mjs` 的 inputManifest/fileSha256；平台 `server/work-source-tools.mjs` 直接复用此同步编辑域。视觉/音频文档编辑也调用 workspace.edit，因此受同一问题影响。

checkpoint 在保存前后各计算一次完整输入指纹，edit 完成后再算一次；输入包含项目二进制素材，本地 MCP 还包含共享 src/scripts/public/锁文件。读取使用同步 fs.readSync，在 HTTP API 主事件循环内执行。

| 合成素材大小 | 批量编辑中位耗时（包含约 30 ms 定时器观测窗口） | 单次指纹读取 |
| --- | --- | --- |
| 无大素材 | 78.74 ms | 约 8 KiB |
| 64 MiB | 666.97 ms | 约 64 MiB |
| 512 MiB | 4,346.01 ms | 约 512 MiB |

独立的小补丁实测 4,374.23 ms，同步读取 **1,610,646,189 字节，约 1.5 GiB**。512 MiB 编辑的事件循环停顿为 **4,250–4,381 ms**。本地 MCP 单次 checkpoint 也耗时约 3,138 ms，事件循环停顿约 3,133 ms。

这是进程级影响：其他作品的 MCP/API 和 WebSocket 消息也可能被拖住。源文件很小不能避免这个代价。当前已有约 304 MiB 的作品输入，不能将风险仅视为遥远的规模问题；没有在真实作品上提交编辑来测其等待时间。

建议：
1. 把内容哈希/冻结输入工作放到异步流或独立 worker，保持取消、错误传播和路径安全检查。
2. 使用每文件内容摘要与不可变素材摘要构建清单，受控编辑只更新受影响的文件，再组合项目指纹；外部变更的可靠失效、文件稳定性复核和明确刷新必须保留。
3. 检查点主要保存可恢复的源码内容；素材版本通过不可变摘要引用。恢复与冻结导出仍验证完整输入，不能通过取消素材验证换取速度。

建议验收：相同 512 MiB 夹具下，热状态的小文本补丁 P50 小于 200 ms，同进程事件循环停顿小于 50 ms；另外覆盖并发外部修改、摘要失效和冻结导出正确性。这些是目标，不是已实现结果。

### P1-2 · 项目锁持有连接，再从同一池申请连接，存在饥饿超时

位置：`server/db.mjs` 的 lock；`server/realtime.mjs` 的 LISTEN；`server/work-source-tools.mjs` 的 source 回调。

连接池 max=12，实时 LISTEN 长期占用一个。db.lock 用专用 client 获得 advisory lock，但回调继续使用 db.one/db.pool.query，从相同池申请第二个连接。所有可用连接同时被持锁操作占住时，后续查询无法推进。

使用真实 db.lock，给不同锁的回调设置同步进入屏障：

| 并发不同锁 | LISTEN 占用 | 结果 |
| --- | --- | --- |
| 11 | 无 | 11/11 成功 |
| 10 | 有 | 10/10 成功 |
| 11 | 有 | 0/11 成功，全部连接获取超时 |

复现把获取超时从生产配置的 10,000 ms 降为 500 ms，以避免长等待。500 ms 的失败是隔离受控复现，并不是生产已发生的超时。当前仅 5 件活跃作品，没有将其描述成已观测的线上故障。

建议让锁内查询复用持锁 client，或采用独立且有上限的锁连接管理，并限制进入持锁区的并发。不要只把 max 从 12 调大：这只移动触发阈值。保留不同进程之间的互斥、失败解锁、只读一致性和取消行为。

建议验收：带 LISTEN 的 20 个不同作品并发操作都能完成；同作品写冲突仍保持正确契约；释放失败不能污染连接池。

### P1-3 · 构建把完整媒体留在内存里，内存按素材总量增长

位置：`scripts/project-assets.mjs` 的 generateBundle；`scripts/render-session.mjs`；`scripts/production-input.mjs` 的 captureInput。

素材插件对 public 下每个文件执行 readFileSync，再将完整 Buffer 交给 emitFile。512 MiB 的素材夹具实测：

- 插件处理约 412 ms；
- emitFile 素材总量约 512 MiB；
- RSS 和 ArrayBuffer 占用分别增加约 **512 MiB**。

这不是最终完整构建的峰值测量；仅插件阶段就已经保留整份素材。输入冻结还会复制和校验素材；Remotion bundler 的 publicDir 复制后又复制一份 films 路径。大媒体、多素材和多执行器并发会同时增加内存、磁盘和等待成本。

建议只把需要打包的源码交给 bundler，大二进制素材使用经过边界校验的流式复制/链接到独立产物目录；保持冻结输入和 no-overwrite 发布。减少同一素材的多份副本，按任务总媒体量做内存/磁盘预算。缓存与链接须绑定不可变内容，不能用可变源路径破坏冻结语义。

建议验收：512 MiB 和 1 GiB 素材下，构建素材阶段额外内存受固定缓冲上限约束，保持资源 URL、Range、音频分包和字幕/导出一致。

### P1-4 · 分页、搜索和上下文冷加载仍遍历完整文件树

位置：`server/project-text.mjs` 的 listSource/project_files_page/project_search；`server/assets.mjs` 的 reconcile/scanReferences；`server/work-operations.mjs` 的 works_context。

文件分页先串行检查完整树，最后才 slice；下一页再次重扫。搜索也先枚举全树，再读候选文件。works_context 即使 detail=false，也调用 assets.list；30 秒缓存失效后会对同仓库所有项目 public 做引用扫描，有些路径还更新 asset_refs。因此不能把 assets.list 当作完全无副作用的生产探针。

| 夹具规模 | 第一页 60 项中位 | 第二页 60 项中位 | 未命中搜索范围 | 冷上下文范围 |
| --- | --- | --- | --- | --- |
| 100 文件 | 25.55 ms | 19.72 ms | 79.6–85.6 ms | 45.9–52.4 ms |
| 2,000 文件 | 306.80 ms | 280.67 ms | 523.0–552.5 ms | 288.5–298.5 ms |
| 8,000 文件 | 1,167.20 ms | 1,150.81 ms | 1,308.3–1,529.1 ms | 1,231.7–1,347.6 ms |

这是大型作品的优先项：AI 小分页不再意味着小开销。context 冷加载的测试仅一个项目、没有大量真实素材引用，尚未计入多作品全仓扫描和实际引用更新的额外成本。

建议以项目修订为键共享文件索引与扫描中的 promise；分页从索引取结果，用有界并发初始化索引。搜索优先使用受控 rg 或索引，但保留文字范围、游标、全文件 SHA、链接与大小检查。把素材引用校对从 compact context 的关键路径移到后台或显式刷新，受控变更做精准失效。

建议验收：8,000 文件热索引下连续分页小于 100 ms；同修订并发读取只初始化一次；compact context 不因无关项目的 public 大目录触发整仓扫描。

### P1-5 · Remotion 反复审片没有复用编译产物

位置：`scripts/render-session.mjs` 的 page；`scripts/remotion-render.mjs` 的 createRemotionRender。

每次创建审片会话都冻结输入。Remotion 分支先进行原生 bundle，再执行 Frame 离线 Vite build，启动两个用途不同的浏览器；原生 bundle 明确设置 enableCaching=false。关闭会话后冻结目录与这些产物一并删除。

320 像素、2 秒示例，独立会话重复两次：

| 引擎 | 首次初始化 | 同源码再次初始化 | 会话内后续单帧 |
| --- | --- | --- | --- |
| Canvas | 2.52 s | 2.11 s | 3.2–4.9 ms |
| Remotion | 16.34 s | 14.33 s | 约 530 ms |

8 个 PNG 成功生成，结果只用于审片启动成本；**不能把 renderStill 的 530 ms 推算为原生整片视频只有约 2 FPS**，整片 MP4 已走 renderMedia 路径。

建议以输入指纹、平台/依赖身份和实际编译参数缓存不可变 bundle；同一组帧请求共享会话与浏览器；单纯视觉截图避免初始化不需要的 Frame 音频构建。区分原生视频、视觉审片、混合音频三种需求，保留字幕、任意时间定位及混合音频正确性。

建议验收：相同冻结输入的第二次单帧/组帧审片不重复完整 bundle，新增热会话在秒级内就绪；改动源码或依赖必定失效。

## 其他链路的审查结果

| 范围 | 已核对的实现与判断 |
| --- | --- |

| AI 聊天 | 页面懒加载、增量事件游标、memo/增量 timeline 已存在；长消息反复 Markdown/代码高亮与无虚拟化的大线程仍是观察点。没有真实长对话浏览器帧耗时，故没有列为已确认 P1 |

## 推进顺序

1. 修复连接池饥饿；将大素材哈希移出 API 事件循环，恢复并发可用性。
2. 改构建素材的内存/复制路径，再做文件索引与 compact context 的扫描分离。
3. 优化 Remotion 审片产物和会话复用。
4. 完成任务状态列投影、工具描述缓存、历史元数据索引和公开静态资源 immutable 缓存。

这一顺序兼顾可用性、大素材创作等待和 AI 高频读取。每阶段用本目录夹具复测，并保留版本冲突、项目边界、冻结输入、字幕/音频及取消行为。不要只调高资源上限或关闭正确性校验。

## 复现材料与验证状态

- `benchmark.mjs` / `results.json`：实际平台和本地 MCP、素材大小、文件分页/搜索/冷上下文、历史和构建素材内存。
- `protocol-benchmark.mjs` / `protocol-results.json`：同业务 API/MCP、工具注册次数、并发轻调用、长状态轮询隐藏数据量。
- `lock-benchmark.mjs` / `lock-results.json`：真实锁实现的受控连接池饥饿与两组对照。
- `render-benchmark.mjs` / `render-results.json`：4 个会话和 8 个 PNG 的审片测量。`frontend-results.json` 为前端补充成功构建。
- `production-readonly.mjs` / `production-results.json`：生产 SELECT-only 元信息/基础查询/EXPLAIN。
- `http-results.json`：公开入口/内容哈希 JS 响应头；HEAD 下 gzip Content-Length 不是实际完整文件传输体积。
- `summary.json`：结构化发现、边界和最新验证结果。
- `reproduce.sh`：创建并清理独立容器与测试库的复现入口。脚本不启动生产 controller，不接入生产库；读取主项目现有依赖，输出只写审查工作树。

运行过程发生过三个测量环境问题，并已修正：夹具过滤误把父 .cache 排除；非 root Chromium 需要可写 XDG 目录；默认 Vite config loader 尝试写入共享只读 node_modules。源码/协议主基准在修正夹具后成功完整重跑，渲染测量在修正 XDG 后成功；前端使用 native config loader 补充构建成功。render-results.json 保留当时 config loader 的失败，frontend-results.json 与 summary.json 给出最新成功结果。这些不是运行时代码的修复，也没有把历史失败覆盖成全部通过。

本次仅运行针对性基准、公开只读请求、前端构建和材料语法/JSON/diff 检查，没有为了审查重复跑整个功能测试套件。临时数据库、基准容器和合成作品在结束后清理；工作树和审查材料保留。
