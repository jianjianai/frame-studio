# Paseo 8.2.5：按实际访问源生成作品连接

## 真实失败与原因

8.2.4 正式生产源码为 `31ff0974bfdd11b1e6b6ba496d7fbcf793e8e7cb`。首次失败截图的 AI 面板显示“Paseo 返回的作品连接范围无效”。只读检查当前生产容器的精选非敏感字段，确认 `FRAME_PUBLIC_URL`、`FRAME_AGENT_URL`、`FRAME_PASEO_FRAME_URL` 均未设置。镜像中的 `server/app.mjs` 正式入口调用无参数 `createApp()`，默认 origin 为 `http://localhost:3000`。

旧网关在安装时固定 origin 和 userScope，session JSON 与 iframe/deep-route HTML 均注入该 origin；公网页面为 HTTPS，父页的严格同源校验因此正确拒绝。现有完整浏览器夹具显式传入本机 origin，未覆盖无公网配置的反代访问。

第二次真实生产验收 `8be188886473485abe768755d80d93b7` 明确复现：session API 200、AI 面板已展开、iframe 数量 0，公开错误仍为“Paseo 返回的作品连接范围无效”，180 秒等待 iframe 超时。此前 7 个现有作品逐一完成三种模式预览，QA PNG/MP4 实际导出通过。该失败不是接受空界面或缩短等待可以消除的定位器问题。根代理保存失败证据；本次没有修改生产、重跑生产或清理。

## 修复

- 新增 `requestExternalOrigin`，使用 Fastify 的 `request.protocol` 与 `request.host`，复用现有受信反代处理，保留非默认端口及 IPv6 authority。
- session 与 iframe HTML 共用该 helper；parentOrigin、userScope 均按当前实际请求访问源生成。深链接和 reload 保留同作品及 nonce。
- 不使用 Origin、Referer 或前端自报值推导地址；显式公共 URL 不变成别名访问白名单，也不要求用户额外配置域名或 TLS。
- 仅接受结构有效的 HTTP/HTTPS authority，在 `manager.ensure` 前验证 origin 与 nonce，畸形请求不启动 daemon。
- workId、basePath、nonce、精确 iframe WindowProxy、消息来源与 MessagePort 校验保持。WS 原有认证和作品 capability 代理保持；HTTP Location 继续重写为同源相对路径，不泄漏 daemon 地址或凭据。

## 聚焦验证范围

新增网关回归覆盖本机 HTTP 非默认端口、IPv6、反代 HTTPS 非默认/默认端口、多 hop、两种别名的独立存储 scope、忽略伪造 Origin/Referer、未受信 proxy headers、结构无效的 authority/nonce 在 ensure 前拒绝。既有 HTTP 二进制转发、17 MiB 二进制 WebSocket、私有凭据替换、cookie 剔除、相对重定向、有界退出断言保留，并通过另一公开别名请求。

新增真实 Chromium 测试运行实际网关、实际生产 `paseoBridge` 与 MessageChannel，使用测试自有 loopback HTTP 及临时 TLS 反代，验证四个 HTTP/HTTPS 访问源、session/HTML 一致 bootstrap、同 nonce 深路由 reload 和 context RPC。iframe 内容为明确的边界夹具，不声称重新验收完整官方 WebUI、模型发送或原生语音；这些由后续完整正式门禁覆盖。
