# MCP 异常退出后的启动锁恢复

## 问题与修复

用户运行 `启动MCP.cmd` 时，配置检查通过，但因 `.secrets/frame-mcp/server.lock` 存在而退出。现场锁属于 PID 19236；操作系统报告该进程已不存在（`ESRCH`），8787 端口无监听。旧实现不区分仍运行的实例与异常退出留下的锁。

- 新增公共启动锁实现，兼容旧 `{pid, token}` 文件。只自动恢复可确认进程已退出的普通文件锁，不结束未知进程，不清空 OAuth 数据。
- 在同一代旧锁的恢复过程中使用独占恢复锁，再核对文件身份、内容及进程状态，避免并行重启删除新实例的锁。
- 正常关闭仅移除本实例的锁。仍运行、状态未知、内容损坏和恢复正在进行分别返回错误码、锁路径及可用的 PID；启动成功时返回 `recoveredLock.pid`。
- 锁损坏、进程权限不足、PID 被复用，以及恢复过程本身被强制中断而遗留的恢复锁，不做猜测性清理；按错误信息检查。使用指南已同步更新。

## 验证

- 7 项新增专项测试通过：活跃实例互斥、旧格式崩溃锁恢复与 OAuth 数据保留、损坏/链接/未知 PID 状态、检查期间锁被替换、恢复中断、初始化/端口绑定失败清理，以及 8 个真实子进程竞争和强制退出后恢复。
- 专项测试初次运行修正了测试代码的 IPC 事件参数读取，以及子进程必须持续存活的设置；修正后专项全部通过。
- `pnpm verify` 完整通过（退出码 0）：5 个工程结构检查零错误/警告、类型检查、111 项单元测试、65 项 MCP 测试、生产构建、22 项浏览器测试，合计 198 项。浏览器测试使用独立端口 `FRAME_TEST_PORT=5197`，未复用 MCP 服务。
- `git diff --check` 通过。没有使用 WSL。

## 本机与公网恢复

- 使用修复后的原 `scripts/mcp-remote.mjs serve` 入口启动后台进程 PID 22324，输出 `recoveredLock.pid = 19236`，恢复旧锁，无人工删除授权目录。
- `.env` 的 SHA-256 与恢复前一致，已有 OAuth grant 和 client ID 全部保留。
- 公网 `https://mcp-shiping.jjaw.cn` 的 OAuth 发现返回 200，匿名 MCP 请求返回 401；官方 SDK 使用现有 Bearer 认证完成初始化和工具发现，共 38 个工具，含全部 5 个语音相关入口。
- 再次启动返回 `SERVER_ALREADY_RUNNING` 和 PID 22324，原实例继续服务。
- 本机和公网 `/healthz` 均返回 HTTP 200、`status: ready`。首次验证误请求 `/health` 返回 404，改为代码定义的 `/healthz` 后通过。
- 启动早期 Cloudflare 曾输出一条 QUIC 连接超时警告；随后公网认证连接成功。本次未修改隧道配置。
- 服务日志、实例信息和健康检查保存在本机忽略目录 `.cache/mcp-service/`，凭据未输出、未入库。未修改其他作品。
- 验证完成后按用户要求停止本次后台 MCP 及其隧道子进程；确认 8787 端口释放、启动锁已清理，交由用户通过 `启动MCP.cmd` 手动启动。
